# النسخة المبسطة المعتمدة للمشروع

هذه الوثيقة هي مرجع التنفيذ والشرح. نطاق المشروع النهائي هو ثلاث صفحات إدارة، أربع نوايا، ثلاث أدوات، واستدعاء Gemini واحد كحد أقصى لكل رسالة.

---

## الصفحة 1 من 3 — فكرة المشروع والمعمارية

### الفكرة بجملة واحدة

يستقبل البوت رسالة النزيل عبر Telegram، ويحدد هل المطلوب إجابة معلوماتية أم عملية فندقية محاكية، ثم يستخدم Gemini لصياغة جواب طبيعي من نتيجة موثوقة ويحفظ السجل في MySQL.

### المشكلة

- موظف الاستقبال يجيب يدوياً عن أسئلة متكررة.
- روبوت القواعد التقليدي لا يفهم الصياغات الطبيعية جيداً.
- نموذج اللغة وحده قد يجيب من عنده أو يطلب عملية غير مسموحة.

### الحل المبسط

```text
Telegram message
       |
       v
FastAPI backend
       |
       v
Simple intent route
       |
       +--------------------+
       |                    |
       v                    v
FAISS evidence        Validated hotel tool
       |                    |
       +---------+----------+
                 v
      One grounded Gemini answer
                 |
        Save trace in MySQL
                 |
                 v
          Reply on Telegram
```

### أين يعمل Gemini؟

بعد تحديد المسار، يستقبل Gemini:

1. رسالة النزيل الحالية.
2. أفضل الفقرات التي وجدها FAISS، أو النتيجة التي أعادتها الأداة المنفذة.

ثم يعيد جواباً منظماً فقط:

```json
{
  "language": "ar",
  "text": "يقدم الفندق الإفطار من الساعة 6:30 حتى 10:30 صباحاً.",
  "basis": "knowledge",
  "evidence_ids": ["retrieved-chunk-id"],
  "tool_names": []
}
```

وعند تنفيذ أداة يكون شكل الجواب:

```json
{
  "language": "ar",
  "text": "توجد غرفة ديلوكس متاحة للفترة المطلوبة.",
  "basis": "tool",
  "evidence_ids": [],
  "tool_names": ["check_room_availability"]
}
```

Gemini لا يصل إلى MySQL ولا ينفذ الأداة بنفسه. FastAPI يحدد المسار ويتحقق من المدخلات وينفذ الكود المسموح، ثم يستخدم Gemini لصياغة جواب طبيعي من النتيجة الموثوقة.

الجملة التي يجب حفظها:

> FastAPI يحدد المسار ويتحقق، وFAISS يجد المعلومة أو الأداة تنفذ العملية، وGemini يصوغ جواباً مؤسساً على النتيجة، وMySQL يحفظ السجل.

## الصفحة 2 من 3 — وظائف النظام

### واجهة النزيل

واجهة النزيل الوحيدة هي Telegram Bot.

### صفحات الإدارة

لا تتجاوز لوحة الإدارة ثلاث صفحات أساسية، بالإضافة إلى تسجيل الدخول:

1. **Dashboard**
   - عدد المحادثات.
   - عدد وثائق المعرفة.
   - عدد الحجوزات.
   - عدد طلبات الخدمة.

2. **Knowledge Base**
   - عرض الوثائق.
   - إضافة وثيقة.
   - حذف وثيقة.
   - إعادة بناء فهرس FAISS بزر واحد.

3. **Conversations**
   - رسالة النزيل.
   - جواب البوت.
   - النية المختارة.
   - هل استخدم Knowledge أم Tool.
   - اسم الأداة المنفذة إن وجدت.

### النوايا الأربع فقط

| النية | مثال | المسار |
| --- | --- | --- |
| `hotel_info` | شو وقت الفطور؟ | FAISS + Gemini |
| `room_availability` | أريد غرفة من تاريخ إلى تاريخ لشخصين | Availability Tool + Gemini |
| `booking_lookup` | أريد متابعة الحجز BKG-2026-0001 | Booking Tool + Gemini |
| `service_request` | المكيف لا يعمل في الغرفة 304 | Service Tool + Gemini |

### الأدوات الثلاث فقط

```text
check_room_availability(check_in, check_out, adults)
lookup_booking(booking_reference, verification_value)
create_service_request(room_number, request_type, description)
```

تجمع الأداة الثالثة الصيانة وخدمة الغرف من خلال `request_type` بدلاً من بناء مسارين منفصلين.

### بيانات MySQL الأساسية

يشرح الطالب ستة جداول منطقية فقط:

```text
knowledge_documents
conversations
messages
rooms
bookings
service_requests
```

لا يلزم في المناقشة شرح جداول التدقيق أو التفاصيل التشغيلية الداخلية.

## الصفحة 3 من 3 — العرض والمناقشة

### العرض العملي

#### 1. سؤال معرفة

```text
شو وقت تقديم الفطور؟
```

الشرح: استرجع FAISS فقرة الإفطار، ثم صاغ Gemini جواباً منها، ولم تُنفذ أداة.

#### 2. عملية توفر غرفة

```text
أريد غرفة من YYYY-MM-DD إلى YYYY-MM-DD لشخصين
```

يجب استبدال التاريخين بتاريخين مستقبليين عند العرض.

الشرح: حدد التطبيق طلب التوفر واستخرج المدخلات، ثم نفذ الأداة واستخدم Gemini لصياغة النتيجة.

#### 3. طلب خدمة

```text
المكيف لا يعمل في الغرفة 304
```

الشرح: صنف التطبيق الرسالة كطلب خدمة، ثم أنشأ الطلب في MySQL من خلال الأداة المسموحة واستخدم Gemini لصياغة الرد.

### أسئلة اللجنة الأساسية

**ما دور Gemini؟**

يصوغ جواباً طبيعياً بلغة النزيل اعتماداً على معلومة FAISS أو نتيجة الأداة فقط، ولا يختلق بيانات فندقية.

**ما دور FAISS؟**

يبحث دلالياً في وثائق الفندق المعتمدة ويعيد أفضل الفقرات المرتبطة بالسؤال.

**ما الفرق بين RAG وTool Calling؟**

RAG يجيب من مستندات الفندق، أما Tool Calling فيطلب تنفيذ عملية برمجية محددة.

**لماذا لا نسمح لـGemini بالوصول إلى قاعدة البيانات؟**

لأن نموذج اللغة يساعد في الفهم والقرار، بينما التحقق والصلاحيات والتنفيذ مسؤولية كود التطبيق.

**ماذا يحدث إذا لم يجد FAISS معلومة؟**

لا يخترع النظام جواباً، بل يخبر النزيل أن المعلومات المعتمدة غير كافية.

**هل العمليات حقيقية؟**

لا. الحجوزات وطلبات الخدمة محاكاة أكاديمية داخل فندق افتراضي.

### ما سيبقى في النسخة النهائية

- FastAPI.
- Telegram Bot.
- Gemini API.
- Sentence Transformers وFAISS.
- MySQL.
- React بثلاث صفحات أساسية.
- Docker وGit.

### ما سيخرج من مسار المشروع الأساسي

- المصنف الهجين متعدد المراحل.
- استدعاء Gemini إضافي لإعادة صياغة السؤال.
- صفحات Hotel Data وEvaluations المنفصلة.
- تفاصيل Prometheus وCaddy من العرض الأكاديمي.
- تعدد مسارات التدقيق والإصدارات في الشرح.
- أي نية أو أداة خارج النوايا الأربع والأدوات الثلاث.

لا تُحذف بيانات الإنتاج في أثناء التبسيط. تُنفذ التغييرات على مراحل، وتُختبر محلياً قبل رفعها إلى GitHub أو الإنتاج.

## مراحل التنفيذ التالية

1. تبسيط مسار الرسالة في Backend إلى استدعاء Gemini واحد كحد أقصى.
2. دمج الأدوات ضمن الأدوات الثلاث المعتمدة.
3. تقليص لوحة React إلى الصفحات الثلاث.
4. إضافة اختبارات محلية بسيطة للحالات الثلاث المعروضة.
5. رفع GitHub ثم نشر آمن على الإنتاج بعد نجاح الاختبارات.
