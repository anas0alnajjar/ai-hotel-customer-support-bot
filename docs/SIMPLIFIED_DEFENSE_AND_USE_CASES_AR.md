# الدليل المبسط للتسليم والمناقشة

## 1. المشروع في صفحة واحدة

**العنوان العربي:** روبوت ذكي لدعم عملاء الفنادق باستخدام نماذج اللغة الكبيرة وتقنية استدعاء الأدوات.

**العنوان الإنكليزي:** AI Hotel Customer Support Bot Using Large Language Models and Tool Calling.

يبني المشروع مساعداً فندقياً يستقبل رسائل النزلاء عبر Telegram، ويفهم الهدف من الرسالة، ثم يختار أحد مسارين:

- سؤال معلوماتي: يبحث في قاعدة المعرفة المعتمدة باستخدام RAG وFAISS، ثم يصوغ جواباً مؤرضاً.
- طلب تنفيذي: يستدعي أداة خلفية مضبوطة بعد التحقق من المدخلات.

النص المركزي الذي يجب حفظه:

> يرسل النزيل رسالة عبر Telegram، ويحدد النظام ما إذا كان يريد معلومة أم تنفيذ إجراء. تذهب الأسئلة المعلوماتية إلى قاعدة المعرفة باستخدام RAG وFAISS، بينما تذهب الطلبات التنفيذية إلى أدوات خلفية مضبوطة بعد التحقق. ثم تُعاد الإجابة إلى Telegram وتُسجّل المحادثات والعمليات في MySQL وتُراقب من لوحة React.

> The guest sends a message through Telegram. The system determines whether the guest needs information or an operation. Informational questions use RAG and FAISS, while operational requests use controlled backend tools after validation. Responses are returned through Telegram, and conversations and operations are stored in MySQL and supervised through the React dashboard.

التقانات الأساسية: Python، FastAPI، React، MySQL، FAISS، Sentence Transformers، Gemini أو النموذج المضبوط، Telegram Bot API، Docker وGit.

## 2. المشكلة والحل

### المشكلة

الرد اليدوي يستهلك وقت موظفي الفندق، والروبوتات التقليدية لا تفهم الصياغات الطبيعية جيداً، والاعتماد على LLM وحده قد ينتج إجابات غير موثقة أو عمليات غير آمنة.

### الحل

معمارية هجينة تفصل الفهم عن التنفيذ:

1. فهم رسالة النزيل وتحديد النية والسياق.
2. إرسال السؤال المعلوماتي إلى RAG.
3. إرسال الطلب التنفيذي إلى Tool Calling.
4. إبقاء التحقق والحالة وقاعدة البيانات وتنفيذ الأدوات ضمن كود التطبيق.
5. حفظ المحادثات والعمليات في MySQL وإظهارها في لوحة الإدارة.

القيمة التطبيقية: إجابات أسرع، عبء أقل على الاستقبال، وعمليات محاكية قابلة للتتبع والاختبار.

## 3. حالات الاستخدام الخمس الأساسية

لا تُعرض في المناقشة أي حالة استخدام أساسية خارج هذه القائمة.

### UC-01 — معلومات الفندق عبر RAG

- الرسالة: `شو وقت تقديم الفطور؟`
- المسار: Knowledge / RAG.
- النتيجة المتوقعة: مطعم الياسمين يقدم الإفطار يومياً من 6:30 حتى 10:30 صباحاً، وفق المستند المعتمد.
- لا تُنفذ أداة فندقية.
- المفهوم: البحث الدلالي ثم إجابة مؤرضة.

### UC-02 — الاستعلام عن حجز قائم

- الرسالة: `أريد متابعة الحجز BKG-2026-0001`
- المسار: Tool Calling.
- السلوك المتوقع: يطلب النظام قيمة التحقق اللازمة، ثم يستعلم عن الحجز ويعرض بيانات آمنة ومقنّعة.
- المفهوم: التحقق قبل الوصول إلى بيانات الحجز.

### UC-03 — التحقق من توفر الغرف

- الرسالة: `أريد غرفة من 2026-08-10 إلى 2026-08-12 لشخصين`
- المسار: Tool Calling.
- النتيجة المتوقعة: عرض الأنواع المتاحة والسعة والسعر الليلي من بيانات MySQL المحاكية.
- المفهوم: استخراج التاريخ وعدد الضيوف وتنفيذ استعلام مضبوط.

### UC-04 — طلب خدمة الغرف

- الرسالة: `جيبلي فطور للغرفة 101`
- المسار: Tool Calling.
- السلوك المتوقع: يلخص النظام الطلب، يطلب التأكيد، ثم ينشئ طلب خدمة ويحصل على مرجع.
- المفهوم: لا كتابة قبل التأكيد، مع منع التكرار.

### UC-05 — طلب صيانة

- الرسالة: `المكيف لا يعمل في الغرفة 304`
- المسار: Tool Calling.
- السلوك المتوقع: يلخص المشكلة، يطلب التأكيد، ثم ينشئ طلب صيانة بمرجع وحالة.
- المفهوم: فهم المشكلة وتحويلها إلى عملية خلفية مضبوطة.

## 4. المعمارية البسيطة

المكونات التي يجب شرحها فقط:

- Telegram Bot: قناة النزيل.
- FastAPI Backend: نقطة التحكم المركزية وواجهات API.
- Intent and Context Understanding: فهم النية والسياق.
- RAG and FAISS: استرجاع معلومات الفندق من المستندات المعتمدة.
- Controlled Hotel Tools: عمليات الحجز والتوفر والخدمة والصيانة.
- Gemini أو LLM مضبوط: المساعدة في الفهم وصياغة الرد.
- MySQL: المحادثات والبيانات والطلبات وسجلات التشغيل.
- React Admin Dashboard: الإدارة والمراقبة.

التدفق المختصر:

```text
Telegram
   ↓
FastAPI
   ↓
Intent decision
   ↓
RAG or Tool Calling
   ↓
MySQL
   ↓
Telegram
```

لوحة React تتصل بـFastAPI لإدارة البيانات ومراقبة المحادثات والطلبات والتقييم.

## 5. مسار المعلومة مقابل مسار العملية

| السؤال | مسار المعلومة | مسار العملية |
| --- | --- | --- |
| ماذا يريد النزيل؟ | معلومة أو سياسة أو موعد | تنفيذ إجراء فندقي |
| المصدر | مستندات Knowledge المعتمدة | بيانات MySQL وأداة مسموحة |
| التقنية | RAG + FAISS | Tool Calling |
| هل يكتب في قاعدة البيانات؟ | لا، باستثناء تسجيل المحادثة | قد يكتب بعد التحقق والتأكيد |
| مثال | وقت الإفطار | إنشاء طلب صيانة |

الكلمة مثل «غرفة» أو «حجز» لا تكفي وحدها لتشغيل أداة؛ المطلوب هو نية تنفيذ واضحة.

## 6. دور الذكاء الاصطناعي

للذكاء الاصطناعي أربع مسؤوليات فقط:

1. فهم الرسائل الطبيعية والعامية.
2. المساعدة في تصنيف النية والسياق.
3. إنشاء تمثيلات دلالية لاسترجاع Knowledge.
4. صياغة رد طبيعي مؤرض في الدليل أو نتيجة الأداة.

حد الأمان الذي يجب حفظه:

> يساعد LLM في فهم الرسالة وصياغة الرد، لكن كود التطبيق يبقى مسؤولاً عن التحقق، وحالة سير العمل، والوصول إلى قاعدة البيانات، والتأكيد، وتنفيذ الأدوات.

> The LLM helps understand the message and formulate the response, but application code remains responsible for validation, workflow state, database access, confirmation, and tool execution.

## 7. RAG مقابل Tool Calling

### RAG

يحوّل السؤال إلى تمثيل دلالي، ويبحث FAISS عن القطع الأقرب، ثم يسمح بالجواب فقط من الأدلة المعتمدة ذات الصلة. المستند المؤرشف أو المسودة غير المعتمدة لا يدخلان الاسترجاع.

### Tool Calling

يختار النظام أداة معروفة مسبقاً، يتحقق من المدخلات، ويطلب التأكيد للعمليات الكتابية، ثم ينفذ الكود العملية في MySQL. النموذج لا ينفذ SQL ولا يقرر صلاحياته بنفسه.

### الفرق بجملة واحدة

RAG يجيب من المعرفة؛ Tool Calling ينفذ عملية مضبوطة.

## 8. الحد الأمني

- الأدوات مسموحة بقائمة محددة.
- المدخلات تتحقق منها نماذج التطبيق قبل التنفيذ.
- العمليات الكتابية الحساسة تحتاج تأكيداً.
- قيم التحقق لا تُرسل إلى LLM كسياق حر.
- قاعدة البيانات ليست متاحة مباشرة للنموذج.
- تسجل المحادثات والعمليات مع إخفاء البيانات الحساسة.
- الرفض المتوقع لطلب غير صالح يعني أن ضوابط الأمان عملت، وليس بالضرورة أن النظام فشل.

## 9. لوحة الإدارة

الأقسام الأساسية الستة:

1. **Overview:** حالة المشروع، عدد المحادثات، عدد مستندات Knowledge، عدد طلبات الخدمة، وصحة النظام.
2. **Conversations:** رسالة النزيل، رد المساعد، النية، ومسار Knowledge أو Tool.
3. **Knowledge:** قائمة المستندات، المحتوى الحالي، الحالة، المحتوى المعتمد الفعال، الاعتماد، الأرشفة أو الاستعادة، وإعادة بناء FAISS.
4. **Hotel Data:** Room Types وRooms وBookings فقط.
5. **Service Requests:** المرجع، النوع، الغرفة، الوصف، الحالة، ووقت الإنشاء.
6. **Evaluations:** ملخص المقاييس الأساسية فقط.

التفاصيل التقنية المتقدمة ليست جزءاً من مسار العرض الأساسي.

## 10. التقييم في صفحة واحدة

| المؤشر | المعنى البسيط |
| --- | --- |
| Intent Accuracy | نسبة الرسائل التي طابقت فيها النية التصنيف المتوقع |
| Recall@K | ظهور الدليل الصحيح ضمن أول K نتائج |
| Top 1 Accuracy | ظهور الدليل الصحيح في المرتبة الأولى |
| Valid Tool Success | نجاح طلبات الأدوات القابلة للتنفيذ |
| Unexpected Tool Failures | حالات الفشل غير المتوقع للأدوات |
| LLM Technical Availability | نجاح الاتصال التقني بالنموذج، وليس صحة كل جواب |

تعرض الصفحة أيضاً:

- Run mode: Offline أو Live.
- نوع نموذج التضمين: اختباري أو إنتاجي مضبوط.

التحذير الإلزامي:

> Offline evaluation does not automatically prove current production performance.

> التقييم غير المتصل لا يثبت تلقائياً أداء نسخة الإنتاج الحالية.

- افتح Telegram وAdmin مسبقاً.

## 12. القيود الحقيقية

1. عمليات الفندق محاكية وليست تشغيلية في فندق حقيقي.
2. لا يوجد تكامل مع PMS حقيقي.
3. توفر وحصة LLM الخارجيان قد يحدان التشغيل الحي.
4. الاسترجاع يعتمد على Knowledge معتمدة وفهرس FAISS حديث.
5. التقييم Offline لا يساوي تحققاً حياً للإنتاج.
6. التقييم البشري للإجابات ما زال محدوداً.
7. Telegram هو قناة النزيل الحالية.

لا ندّعي أن كل إجابة Knowledge صحيحة؛ نقلل الخطأ بالاعتماد والمزامنة والتحقق من صلة الدليل.

## 13. عشرون سؤالاً متوقعاً من اللجنة

### 1. ما المشكلة التي يحلها المشروع؟

يقلل وقت الرد والعبء على موظفي الفندق، ويجمع الإجابة المعلوماتية والعمليات المحاكية في مساعد واحد.

### 2. لماذا لا تستخدمون LLM وحده؟

لأن LLM قد يهلوس ولا يجب أن يصل مباشرة إلى قاعدة البيانات؛ لذلك فصلنا الفهم والصياغة عن الاسترجاع والتنفيذ.

### 3. ما الفرق بين RAG وTool Calling؟

RAG يسترجع معرفة ويجيب منها، بينما Tool Calling ينفذ عملية برمجية محددة.

### 4. لماذا FAISS؟

للبحث السريع بالتشابه الدلالي داخل تمثيلات مستندات الفندق.

### 5. ما دور Sentence Transformers؟

تحويل النصوص والأسئلة إلى متجهات دلالية قابلة للمقارنة داخل FAISS.

### 6. ما دور Gemini؟

المساعدة في فهم الرسالة وصياغة الرد؛ لا ينفذ قاعدة البيانات أو الأدوات مباشرة.

### 7. أين تُحفظ البيانات؟

المحادثات وبيانات الفندق والطلبات وسجلات التشغيل في MySQL، ومؤشر البحث في FAISS.

### 8. كيف تمنعون تنفيذ أداة خاطئة؟

النية تحدد المسار، والأدوات ضمن قائمة مسموحة، والمدخلات تتحقق برمجياً قبل التنفيذ.

### 9. لماذا تطلبون التأكيد؟

لمنع إنشاء طلب خدمة أو صيانة بالخطأ قبل عملية الكتابة.

### 10. ماذا يحدث عند انقطاع Gemini؟

تستخدم المسارات الحتمية والأدوات قوالب fallback مضبوطة، ويُعلن التعذر عند عدم توفر جواب آمن.

### 11. كيف تمنعون الهلوسة في معلومات الفندق؟

يجب أن يكون الجواب مؤسساً على دليل مسترجع من مستند معتمد ومرتبط بالسؤال.

### 12. ماذا يحدث للمستند المؤرشف؟

يبقى محفوظاً في MySQL لكنه يُستبعد من الاسترجاع وFAISS الفعال.

### 13. هل المسودة تدخل RAG؟

لا؛ المؤهل هو المحتوى المعتمد الفعال ضمن مستند نشط.

### 14. لماذا FastAPI؟

لأنه مناسب لبناء API واضحة وسريعة في Python، مع تحقق قوي من المدخلات ودعم async.

### 15. لماذا React؟

لبناء لوحة إدارة تفاعلية تراقب المحادثات والمعرفة والطلبات والتقييم.

### 16. ما معنى Intent Accuracy؟

نسبة رسائل الاختبار التي طابق فيها تصنيف النية القيمة المتوقعة.

### 17. ما الفرق بين Recall@K وTop 1؟

Recall@K يقبل وجود الدليل ضمن أول K نتائج، بينما Top 1 يشترط أن يكون الأول.

### 18. هل 100% LLM availability تعني جواباً صحيحاً؟

لا؛ تعني فقط أن الاتصال التقني بالمزود نجح.

### 19. هل النظام مرتبط بفندق حقيقي؟

لا، العمليات الخلفية محاكية ضمن نطاق المشروع الأكاديمي.

### 20. ما التطوير المستقبلي الأهم؟

تكامل PMS حقيقي، بيانات وتقييم بشري أوسع، ومراقبة إنتاجية طويلة المدى.

## 14. ورقة الحفظ من صفحتين

### الصفحة الأولى — ما هو المشروع؟

- مساعد فندقي عبر Telegram.
- FastAPI يقرر Information أو Operation.
- Information → RAG + FAISS → دليل معتمد.
- Operation → Tool Calling → تحقق وتأكيد → MySQL.
- React Admin للمراقبة والإدارة.
- خمس حالات فقط: معلومات، حجز، توفر، خدمة غرف، صيانة.
- LLM يفهم ويصيغ، لكن التطبيق يتحقق وينفذ.

الجملة الذهبية:

> RAG يجيب من المعرفة، وTool Calling ينفذ عملية مضبوطة، وكود التطبيق هو حد الأمان بينهما.

أمثلة الحفظ:

```text
شو وقت تقديم الفطور؟                         → RAG
أريد متابعة الحجز BKG-2026-0001             → Booking Tool
أريد غرفة من 2026-08-10 إلى 2026-08-12 لشخصين → Availability Tool
جيبلي فطور للغرفة 101                        → Room Service Tool
المكيف لا يعمل في الغرفة 304                 → Maintenance Tool
```

### الصفحة الثانية — ماذا أدافع؟

- لا يوجد PMS حقيقي؛ العمليات محاكاة.
- لا يُسمح للنموذج بتنفيذ SQL أو أداة مباشرة.
- الأسئلة المعلوماتية تحتاج مستنداً معتمداً وFAISS حديثاً.
- عمليات الكتابة تحتاج تحققاً وتأكيداً.
- MySQL يحفظ السجل، وAdmin يظهر المحادثة والطلب.
- Offline evaluation ليس production validation.
- LLM availability ليست answer accuracy.
- عند نفاد الحصة توجد fallbacks مضبوطة، ولا نخترع جواباً غير موثق.

ترتيب العرض:

1. إفطار عبر RAG.
2. توفر غرفة عبر Tool.
3. خدمة غرف مع تأكيد.
4. المحادثة والطلب في Admin.
5. Knowledge وFAISS.
6. Evaluation summary.

## 15. ملحق تقني قصير

المشروع يحتوي داخلياً على قدرات إضافية لحماية التشغيل وتحسينه، لكنها ليست حالات استخدام أساسية في التسليم، ومنها: متابعة بعض حالات الطلبات، دعم لغوي إضافي، استيضاح متقدم، سجل نسخ Knowledge، تدقيق تشغيلي، وسياسات تشغيل Docker.

هذه القدرات لا تغيّر المعمارية الأساسية ولا تدخل سيناريو العرض. عند سؤال تقني مباشر يمكن القول إن النظام مصمم بطبقات منفصلة: قناة Telegram، API، فهم النية والسياق، RAG، أدوات مضبوطة، تخزين MySQL، ولوحة React. التفاصيل الداخلية موجودة في الكود والاختبارات، لكن الدفاع يركز على النطاق الأكاديمي المعتمد وحالات الاستخدام الخمس.
